01

先搞清楚：项目在干什么

动手读代码之前，先建立一张地图。不然后面每个文件你都不知道在解决什么问题。

视频流 (mp4 / 摄像头) │ ├─ 【算法 0】RTMPose + SimCC 解码 → 17 个关键点 (T, 17, 3) │ io/pose_infer.py │ ├─ 【算法 1】One-Euro Filter → 去抖（关键点不抖了） │ postprocess/filters.py │ ├─ 【算法 2】身体坐标系归一化 → 位置/尺度/朝向无关 │ postprocess/normalize.py │ ├─ 【算法 4】因果流式 Transformer → 逐帧类别概率 (T, C) │ models/streaming.py │ ├─ 【算法 6】Viterbi 动态规划 ┐ ├─ 【算法 7】Hysteresis 双阈值 ├→ 干净的动作段 ├─ 【算法 8】最小持续时长约束 ┘ │ postprocess/decode.py │ └─ 输出: [{"start":0.0, "end":1.2, "label":"左举手", "confidence":0.94}, ...]
关键心智模型

这个项目是三层，不是两层。

① 姿态识别（算法 0）→ 每帧骨架，这是几何事实

② 动作分类（算法 4）→ 每帧类别，这是语义标签

③ 时序解码（算法 6-8）→ 动作段，这是时空结构

②③ 缺一不可：只有 ①② 你知道每帧是什么，但输出是碎帧、没有时间戳； 只有 ①③ 你能把视频切成段，但不知道每段是什么动作。

代码地图：哪个文件放什么

文件核心类 / 函数职责

03

算法 1-3：输入侧三个手写件

这三个算法都在「模型之前」，作用是把原始关键点变成模型爱吃的干净输入。

算法 1

One-Euro Filter

位置：actionflow/postprocess/filters.py → class OneEuroFilter (第 43 行)
封装：同文件 class SkeletonFilter (第 137 行) —— 对 17×3 个坐标各建一个滤波器
它解决什么问题
RTMPose 是逐帧独立检测的。人在站着不动时，检测出来的坐标依然会抖 ±3 像素。 这种抖动会让「骨长」这类几何特征剧烈变化，模型的输入分布直接崩掉。
核心公式
cutoff = min_cutoff + beta * |速度|
α     = 1 / (1 + τ / (2π · cutoff))     τ = 1/dt

滤波值 = α · 当前值 + (1 - α) · 上一个滤波值
关键在 cutoff 那一行：速度越快，cutoff 越高，α 越接近 1，滤波越弱。 慢动作时强滤波（去抖），快动作时弱滤波（不拖影）。
为什么 beta 默认是 0
检测噪声本身会产生很大的表观速度。beta 偏大会把噪声误判成「快速运动」， 反而削弱滤波。实测（σ=3px 噪声下）：beta=0.02 只降 19% 抖动， beta=0.00 降 37%。所以默认 0，只在确实关心「挥手不能有拖影」时才调大。
怎么验证它是对的
python tests/test_postprocess.py —— 15 个测试里有一半是滤波的。
最有说服力的是：喂一段带已知抖动的信号进去，检查输出的抖动方差确实变小， 同时信号的形状没有变（不能滤成一条直线）。
算法 2

身体坐标系归一化

位置：actionflow/postprocess/normalize.py → function normalize_keypoints (第 125 行)
配套：compute_origin / compute_scale / compute_rotation（第 74/80/103 行）
批处理版：normalize_sequence (第 171 行) —— 训练时对整段用
它解决什么问题
让模型学「动作」，而不是学「这个人在画面里的位置和体型」。三步：
步骤1  原点 = 左右髋中心 (kps[11] + kps[12]) / 2
步骤2  尺度 = 躯干长度 = |kps[5] - kps[11]|
步骤3  朝向 = 躯干向量归一化 → 旋转到标准朝向
步骤4  每个关键点 p → (p - 原点) / 尺度，再旋转
为什么必须做
  • 人在画面左边还是右边 → 不该影响「抬左手」
  • 身高 160 还是 190 → 不该影响「抬手」
  • 转身 90° → 旋转到标准朝向后依然能识别
不做归一化的话，同一个动作在画面不同位置会被当成不同特征， 训练集必须覆盖各种位置才学得会 —— 数据量直接爆炸。
两个容易踩的坑
  • 归一化两次：npz 里存像素坐标，归一化只在「喂给模型前」发生一次。 归一化两次 ≠ 归一化一次（两次的旋转会互相抵消，实测坐标最大差 2.9）。 见 annotate.py::extract_keypoints 里 cfg.norm.enabled = False 那行。
  • 尺度模式：torso（默认）用躯干长， bone_median 用所有骨长的中位数，对遮挡更鲁棒。
怎么验证它是对的
python tools/verify_pipeline.py 里的「检查 2」： 同一段骨架，人为平移 / 缩放 / 旋转，归一化后的结果应该一模一样。
算法 3

关节嵌入 + 时间位置编码

位置：actionflow/models/classifier.py → class SkeletonEmbedding (第 44 行)
使用者：SkeletonTransformerClassifier / CausalStreamingClassifier 共用
它做什么
把 (B, T, 17, 3) 的骨架变成 Transformer 能吃的 token 序列 (B, T×17, 128)。 三样东西相加：
coord_proj (x,y,conf) → Linear(3, 128)     ← 坐标长什么样
+ joint_embed[j]     (17, 128)          ← 这是哪个关节
+ time_embed[t]      (64, 128)          ← 这是第几帧
= reshape (B, T*17, 128)
为什么需要 joint_embed
光有坐标，模型不知道「这个坐标是左手腕还是右膝盖」。 关节身份必须显式编码进去，否则「左手腕」和「右手腕」在数值上完全一样。
为什么需要 time_embed
告诉模型「这是序列的第几帧」。注意：推理时不能整段视频一次喂进去 —— time_embed 是 nn.Embedding(64)，只覆盖 64 帧； 整段上千帧会直接 IndexError。所以推理必须按 32 帧窗口滑。
怎么验证它是对的
看 tests/test_model.py： test_build_model_from_config 检查形状， test_backward_pass_works 检查能反向传播。
04

算法 4-5：模型侧两个核心件

这是整个项目最难、也最有价值的一块。读懂因果掩码，你就理解了「流式」这两个字。

算法 4

因果注意力掩码 ★核心

位置：actionflow/models/streaming.py → function build_causal_frame_mask (第 99 行)
调用方：class CausalStreamingClassifier → build_masks (第 246 行)
测试：tests/test_streaming.py → 19 个测试，全是这块的
它解决什么问题
普通 Transformer 是「上帝视角」—— 第 3 帧能看到第 8 帧。 离线视频里这没问题，但实时流里是致命的： 用户已经看到的第 3 帧结果，会因为你后来又来了 5 帧而偷偷改变。
通俗解释
注意力机制就像开会，每个 token 都要听所有人发言。 因果掩码就是规定「只能听前面的人的发言，不能听后面的」—— 这样第 3 帧的结论一旦算出来就永远不会变。
⚠️ 本项目最大的一个坑
掩码必须按帧号算，不能按 token 号算。
token 编号 = 帧号 × 关节数 + 关节编号

按 token 编号做下三角掩码 → 同一帧内的 17 个关节互相看不见 ❌
  （左手腕看不到左手肩 —— 这在物理上说不通）

按帧号做掩码 → 同帧内 17 个关节互相可见，帧与帧之间才因果 ✅
build_causal_frame_mask 里就是按 t_of[i] = i // num_joints 分组的：同一帧的 token 之间 mask 全部可见，跨帧才因果。
验收标准：前缀不变性
「用前 t 帧算出的结果」
  必须  ==  「用前 t+100 帧算出的前 t 帧」
不是「差不多就行」，是逐位相同。实测：streaming = 0.0（完全一样）， boundary < 1e-5，fusion < 1e-5。
这条测试在 tests/test_streaming.py::test_prefix_invariance_exact， 任何改动破坏了它都会立刻挂掉。
为什么这是必须独立测的
因为流式架构的错误在离线测试里是看不出来的。 假设模型不小心让第 3 帧看到了第 8 帧：离线推理把整段视频喂进去，结果看着挺好、测试全绿； 实时推理时用户已经看到「抬手」，下一秒突然变成「站立」—— 因为新帧到了。
怎么验证它是对的
python tests/test_streaming.py —— 19 个测试。
最核心的一个：构造两段长度不同的输入（前 32 帧 vs 前 132 帧）， 检查前 32 帧的输出逐位相同。
另外 examples/architectures.py 也会现场演示这个性质。
算法 5

Key-Padding Mask（处理漏检）

位置：actionflow/models/streaming.py → class CausalStreamingClassifier.build_masks (第 246 行)
同类实现：models/classifier.py → SkeletonTransformerClassifier.build_masks (第 156 行)
它解决什么问题
姿态模型有时会漏检某个关节（置信度低）。这个关节的坐标这时是垃圾值。 如果让它参与注意力，垃圾就会污染整段序列的判断。
怎么做
把置信度低于阈值（默认 0.3）的关节标记出来， 用 src_key_padding_mask 让它们不参与注意力的 key。
⚠️ 与 ONNX 导出冲突
这个 mask 会导致 dynamo 导出器崩溃 （GuardOnDataDependentSymNode）， 因为「哪些 token 被屏蔽」是数据依赖的，而 dynamo 要求形状编译期确定。 所以导出必须用旧版导出器（dynamo=False）—— 细节见 models/streaming.py::export_streaming_onnx 的 docstring。
怎么验证它是对的
tests/test_streaming.py 里构造一批「某个关节置信度=0」的输入， 检查输出不崩、且结果合理。
05

算法 6-8：输出侧三个手写件

这三个算法都在同一个文件里：actionflow/postprocess/decode.py。它们治三种不同的病。

为什么必须有解码层

逐帧独立分类会产生三类错误，而三个算法各治一种：

① 段被劈碎 —— 中间一帧误判，一个连续动作被切成两段 → 算法 7 治

② 孤立假阳性 —— 某帧置信度突增，输出一个 0.03s 的不可能动作 → 算法 6 治

③ 边界抖动 —— 同一动作两次推理起止帧差 3~5 帧 → 算法 8 + 边界回归治

多数开源动作识别项目只做到 Layer 2 就停了，直接把 argmax 当输出，边界全是碎的。

算法 6

Viterbi 动态规划

位置：actionflow/postprocess/decode.py → function viterbi_decode (第 178 行)
平滑版：function viterbi_smooth_probs (第 225 行) —— 实际用的是这个
转移矩阵：function build_transition_matrix (第 151 行)
测试：tests/test_decode.py
它解决什么问题
逐帧独立看，第 35 帧偶尔会被误判成一个完全不相干的动作， 把一个连续动作从中间劈成两半。Viterbi 从全局找一条最合理的路径， 把这孤立的误判拉回来。
核心公式
dp[t][c] = log P(c | t) + max over c' ( dp[t-1][c'] + log T(c'→c) )

T(c→c) 转移概率：
  留在同一类  stay_prob   = 0.9   （默认）
  切到别的类  switch_prob = 0.05  （默认）
直观理解：一个动作不会只持续一帧就消失。所以「切到别的类」要付出代价， 只有整体收益更高时才会切。
两个函数的区别（容易搞混）
  • viterbi_decode → 返回类别序列（argmax 的路径）
  • viterbi_smooth_probs → 返回平滑后的概率（保留置信度信息）
实际解码走的是后者，因为后面 Hysteresis 需要连续的置信度值来跨阈值。
怎么验证它是对的
最直观的验证方式：python -m actionflow.cli decode-test
它会手工构造一段带噪声的概率序列，注入三种典型错误，然后逐层对比：
  • 朴素 argmax → 一堆碎片（12 段）
  • 只加 Hysteresis → 段数减少但仍有问题
  • 加 Viterbi → 路径连续，误判被拉回
  • 完整解码 → 干净的 4 段
这个演示是理解整个解码层的最佳入口，强烈建议先跑一遍。
算法 7

Hysteresis 双阈值（迟滞回环）

位置：actionflow/postprocess/decode.py → function hysteresis_threshold (第 69 行)
测试：tests/test_decode.py
它解决什么问题
用单一阈值切段，置信度在阈值附近抖动时，段的开头结尾会跟着抖。 同一段视频跑两次，起止帧能差 3~5 帧。
核心机制
high = 0.7   置信度跨过它 → 开段
low  = 0.4   置信度跌到它以下 → 关段

普通阈值：  0.65 ─┬─ 0.62 ─┬─ 0.68    ← 抖成三段
双阈值：    0.65 ┬────── 0.68          ← 一段到底
和 Canny 边缘检测的思路完全一样：高阈值确认「有」，低阈值确认「继续有」。
和 Viterbi 的分工
Viterbi 治「孤立误判」（一次性的错）， Hysteresis 治「持续抖动」（边界附近的来回摆动）。 两者治的病不一样，不能互相替代。
怎么验证它是对的
python -m actionflow.cli decode-test 的「【2】Hysteresis 双阈值」那一段， 会直接对比「朴素 argmax」和「双阈值」的段数。
算法 8

最小持续时长约束

位置：actionflow/postprocess/decode.py → function decode_segments (第 276 行)， 第 3 步「最小持续时长约束」
参数：DecodeConfig.min_duration（默认 0.3 秒）→ actionflow/core/config.py
它解决什么问题
某帧置信度突然飙到 0.85，会产生一个 0.03 秒的孤立假段。 但人不会做 0.03 秒的动作 —— 这在物理上就不可能。
怎么做
min_frames = max(1, round(min_duration * fps))   # 0.3s @30fps = 9 帧
丢掉所有 (end - start) < min_frames 的段
参数怎么调
  • 调大 → 更少假阳性，但也可能把真动作切掉（动作太短）
  • 调小 → 更灵敏，但假阳性变多
  • 默认 0.3 秒对「抬手」「踢腿」这种动作合适
怎么验证它是对的
decode-test 的「【4】完整解码」会注入一个 0.03s 的假阳性段， 看它有没有被滤掉。
decode_segments 的完整流水线

上面三个算法在 decode_segments() 里是按顺序调用的，顺序不能乱：

1. Viterbi 平滑          → 消除孤立误判
2. Hysteresis 切段       → 得到候选段
3. 最小持续时长约束      → 滤除假阳性段
4. 相邻同类段合并        → 消除不必要的碎片（merge_gap，默认关）
5. 转成带时间戳的 ActionSegment

换个问法
头问的问题性质
分类头「这一帧是什么动作？」离散、粗糙
边界回归头「这一帧距最近的边界还有几帧？」连续、精细
核心公式
输出两个非负距离（用 softplus 保证非负）：
  dist_to_start[t] = 这一帧距「它所属那一段」的起点还有几帧
  dist_to_end[t]   = 这一帧距「它所属那一段」的终点还有几帧

反算边界位置：
  起点 = t - dist_to_start[t]
  终点 = t + dist_to_end[t] + 1        （终点是开区间）
⚠️ 边界帧是「歧义帧」—— 为什么要用中位数
假设真值是「抬手=[30,70)，站立=[70,120)」，但 Hysteresis 迟到了，把边界切在 69。 第 69 帧被分给了「站立」，可真值里它属于「抬手」。
  • 按「站立」的语义读 → 距站立起点 0 帧 → 边界就在 69 ✓
  • 按「抬手」的语义读 → 距抬手起点 39 帧 → 边界在 30 ✓
两种读法在数值上都合法，光看这一帧根本分不出来。 但段内部的每一帧都指向同一个答案 —— 抬手段内的第 40 帧说 「距起点 10 帧」→ 起点 = 40 − 10 = 30，句句都指向 30。 
所以做法是：不信门口那一帧，看屋里的人怎么说的，取多数意见（中位数）。
一两个异常值带不偏结果。
修正算法的三遍
第 1 遍: 对段内帧做中位数统计，估计这一段真正的起点/终点
第 2 遍: 解决相邻段的冲突（边界是「共享资源」,谁挪了就大家都挪）
第 3 遍: 重算置信度
⚠️ 训练时的两个硬约束
  • 必须有帧级标签：只有段标签的话，窗口内所有帧标签都一样， 算出来的「到边界的距离」全是 0 —— 学不到任何东西，还会用垃圾目标污染梯度。 代码里直接跳过边界损失。
  • 必须用绝对帧号：推理时 起点 = t - dist[t] 里的 t 是视频绝对帧号，所以训练目标也必须是绝对距离。见 compute_boundary_targets 的 docstring。
怎么验证它是对的
python tests/test_boundary.py —— 25 个测试。 重点看中位数消歧那个 case：构造一个「边界帧有歧义」的场景， 检查算法仍然能找回正确边界。

附加件：双路融合（可选架构）

--arch fusion 启用。骨架路 + 视频路 Cross-Attention。

附加

Cross-Attention 双路融合

位置：actionflow/models/fusion.py
→ class VideoBackbone (第 120 行) —— 抽象接口
→ class SimpleVideoBackbone (第 154 行) —— 自带的轻量实现
→ class CrossAttentionFusion (第 223 行) ★核心
→ class FusionClassifier (第 377 行)
测试：tests/test_fusion.py → 15 个
它解决什么问题
骨架路看到的是几何，看不到语义。举几个例子：
  • 「拿起杯子」和「拿起手机」—— 手的位置一样，但手里有东西 vs 手里是空的，骨架完全一样
  • 「开门」和「挥手」—— 手的轨迹可能相似，但门把手的有无不同
  • 「走路」和「跑步」—— 关节角度接近，但步频、步幅不同
融合方式
骨架路问视频路：「这一帧画面上有什么？」 → 得到 语义补充
视频路问骨架路：「这个人怎么动的？」     → 得到 几何引导
通俗讲：Cross-Attention 就像「查字典」。骨架特征是查询词，视频特征是字典， 每个骨架 token 问「和我最相关的画面信息是什么」，注意力算出相关度，加权求和。
关键设计：残差连接
融合 = 骨架原样 + 视频补充
即使视频路认错了（画面里有干扰物），骨架信息还在， 模型顶多「参考了一下错误意见」，不会彻底跑偏。
VideoBackbone 是抽象接口
接什么都能用：
from torchvision.models.video import swin3d_t
net = swin3d_t(weights="DEFAULT")   # 换成任意预训练视频 backbone
本仓库自带的 SimpleVideoBackbone（3× Conv3d）只用于跑通链路和测试， 不用于刷 SOTA。默认配置仍是骨架路（0.29M 参数，端侧可跑）。
⚠️ 交叉注意力也必须加因果掩码
否则第 3 帧会去看第 8 帧的视频特征，一样破坏前缀不变性。 见 fusion.py::FusionClassifier.forward 里的注释。
怎么验证它是对的
python tests/test_fusion.py —— 15 个测试。 重点：融合后仍然满足前缀不变性（fusion < 1e-5）。

最有效的学习方式：改参数看变化

每个算法都有一段「魔数」可以调。逐个改，观察输出怎么变，比读十遍代码管用。

  • DecodeConfig.high_threshold 0.7 → 0.9：段会变少、误检变少
  • DecodeConfig.min_duration 0.3 → 1.0：短动作被滤掉
  • FilterConfig.beta 0 → 0.5：快速动作开始有拖影
  • FilterConfig.min_cutoff 1.0 → 0.3：抖动更小但延迟更大
  • ModelConfig.window 32 → 16：时间戳更细，但上下文更少

参数全在 actionflow/core/config.py，一个 dataclass 集中管理。

常见困惑 FAQ

Q · 为什么要分三层，不能一个模型端到端出时间戳吗？

可以，但会很难。姿态层是几何事实（手在哪），分类层是语义（这是什么动作）， 解码层是时空结构（何时起止）。三层解耦的好处是： ① 姿态模型现成不用训；② 分类层只需要骨架序列，数据量小得多； ③ 解码层是纯算法，可以用清晰���规则把边界收拾干净，而且可解释、可调。

Q · 因果掩码和 Key-Padding Mask 有什么区别？

  • Causal Mask（算法 4）：限制「时间维度」—— 第 t 帧不能看 t 之后的帧。这是流式的核心。
  • Key-Padding Mask（算法 5）：限制「无效数据」—— 置信度低的关节不参与注意力。这是数据质量的处理。
两者是叠加的，不是二选一。

Q · 为什么不用现成的视频模型（VideoMAE / TimeSformer）？

三个原因：① 端侧算力约束 —— 视频模型动辄几亿参数； ② 原子动作需要结构化可解释 —— 骨架直接对应关节语义； ③ 流式因果需求 —— 视频模型大多需要整段输入。 另外骨架路在小数据下有先验优势：关节位置本身已经编码了大量运动信息。

Q · 为什么不用 ST-GCN 这种图卷积？

骨架确实是图结构，图卷积是合理选择。但 自注意力能直接建模任意两个关节的相对关系 （左手相对右手在哪），不依赖固定的邻接矩阵；而且并行友好、感受野更直接。 代价是 T² 复杂度 —— 靠 T=32 的窗口控制住。 两者都是这个领域的必知基线，值得对照着看。

Q · `--arch` 四个架构怎么选？

arch什么时候用
offline只做 baseline 对比，不上生产
streaming默认。实时 / 端侧部署
boundary需要更准的时间戳时
fusion骨架分不清的语义动作（拿杯子 vs 拿手机）

Q · 为什么模型只有 0.29M 参数？会不会太小了？

不会。输入是 17 个关节 × 3 个数（不是像素），信息密度极高。 真正吃算力的是姿态提取（RTMPose，54MB），不是分类器。 而且分类层要处理的是「17 个点的时序运动」这种低维信号，不需要很大的模型。

Q · 前缀不变性到底怎么算的？

见 tests/test_streaming.py::test_prefix_invariance_exact。 核心就是构造两段长度不同的输入（skel[:32] 和 skel[:132]）， 对比它们前 32 帧的输出是否逐位相同。 你可以直接打开这个测试看，它写得比文档清楚。
